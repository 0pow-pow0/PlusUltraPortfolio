    🗿 State Machine a Bitmask | Bitwise Flags & Manual State Management

    🧭 CONTEXT

    Allora, il player. Dovevo sapere se stesse fermo, corresse, saltasse, cadesse, sparasse. Ovviamente, la risposta giusta era utilizzare una state machine, magari sfruttando un'architettura divisa in classi che poi convergesso, per composizione, dentro uno script che li gestisse. Come fatto per RumbleSmash - Portfolio - IT|Rumble Smash.

    Però, io sono fico 😎.

    Dunque, ho optato per gestire gli stati attraverso i bit (mi diverto, vero?) e delle bitmask. Teoricamente attraverso un approccio classico per le state machine, se io sto saltando e sparando e supponiamo che quando sono in questo stato subisco il doppio dei danni, posso creare un nuovo pseudostato per gestire interazioni e comportamenti speciali, risolvendo, dunque, questo problema.

    Invece, con le bitmask è leggermento diverso, perché per verificare se io mi trovo in due stati contemporanemente mi basta applicare due maschere allo stesso tempo.

    Supponiamo che

    States 
    // 8 bit, ogni bit rappresenta uno stato.
unsigned char current_active_states = 0;

const int STATE_STILL     = 0b1;
const int STATE_RUNNING   = 0b10;
const int STATE_JUMPING   = 0b100;
const int STATE_FALLING   = 0b1000;
const int STATE_SHOOTING  = 0b10000;

    Per gestire i comportamenti derivanti dall'attivazione di 2 stati o piu' faccio:

    Controllare lo stato 
    if ((current_active_states & STATE_JUMPING) && (current_active_states & STATE_SHOOTING))
{
	damageMultiplier = 2f;
}

    ❓ WHY?

    Perché i bit e le bitmask invece di enum/state pattern classico?

    Il vero motivo era imparare a gestire i bit e manipolarli, dunque era più un caso di studio che una vera e propria scelta architetturale, ma vediamo comunque quali vantaggi esistono in questa architettura.

    • Coesistenza di stati: collision_mask può avere GROUND | RIGHT_SIDE insieme, con altri metodi dovrei creare pseudostati.

    • Performance: state_mask & STATE_JUMPING Le operazioni binarie sono semplicissime, in pratica perfetto se voglio programmare ROM per il mio amato Game Boy Advance (è successo), dove l'ottimizzazione è alla base.

    • Memoria: 1 unsigned char significa 8 stati in 1 byte.

    • Estensibilità: aggiungere STATE_DASHING = 0b100000 non tocca codice esistente,

    Inoltre, la semplicità del gioco mi ha permesso di optare per questa soluzione, chiaramente per sistemi più complessi, avrei dovuto adottare altre scelte.

    🛠️ HOW

    Ho creato una classe player e dopodiché ho aggiunto un parametro per contenere i vari stati e il bit a cui corrisponde ogni stato.

    Classe Player 
    class Player
{
	// Definizione flag 
	typedef unsigned char ENTITY_STATE;
	public const int STATE_STILL     = 0b1;
	public const int STATE_RUNNING   = 0b10;
	public const int STATE_JUMPING   = 0b100;
	public const int STATE_FALLING   = 0b1000;
	public const int STATE_SHOOTING  = 0b10000;
	
	typedef int COLLISION_TYPE;
	const int COLLISION_TYPE_GROUND     = 0b1;
	const int COLLISION_TYPE_CEILING    = 0b10;
	const int COLLISION_TYPE_LEFT_SIDE  = 0b100;
	const int COLLISION_TYPE_RIGHT_SIDE = 0b1000;
	
	// Check O(1)
	public bool is_entity_state(ENTITY_STATE s);
	
	// Setter semplice
	public void set_entity_state(ENTITY_STATE new_state);
}

    ⚽ Sistema di Collisione | Per-Char collision detection

    🧭 CONTEXT

    Dovevo creare le collisioni all'interno del gioco, dunque, per un gioco eseguito in console, l'unica un'opzione era un array bidimensionale di caratteri. Mi serviva, oltre che avere dei "blocchi" diversi, era necessario che ognuno avesse un behaviour diverso, alcuni "blocchi" dovevano bloccarmi il giocatore, altri no, se poi avessi voluto creare nuovi behaviour per altri blocchi, dovevo rendere il codice estensibile per questo fine.

    Dunque, ho sostanzialmente creato una "tilemap" fatta di unsigned char, dove:

    • '=': piattaforme

    • 'I' = muri

    • ' ' = vuoto.

    Dopo aver risolto il problema della mappa, era necessario che creassi un sistema di collisioni, l'idea era quella di sviluppare un simil AABB con continuous collision detection, la CCD era necessaria, altrimenti qualunque movimento superiore ad un "tile" avrebbe rotto le collisioni. Il risultato è un algoritmo che controlla la mesh del personaggio e che suddivide il movimento in "step", ognuno dei quali viene verificato, non appena si verificare una collisione, l'entità viene traslata di un valore pari alla distanza tra la posizione iniziale dell'entità e la prima collisione verificatasi, per un progetto basato solamente su forme semplici, è perfetto, magari non il meglio dell'ottimizzazione.

    Ogni step verificato, la mesh del personaggio viene interamente controllato l'overlap con i tile della mappa, visto che le mesh sono fatte da caratteri ASCII, viene controllato ogni carattere in World Space per verificare se sono avvenute collisioni. Per abbreviare, questo algoritmo di CCD per-char viene detto CCDPC.

    ❓ WHY?

    Perché hai scelto l'algoritmo CCDPC?

    Verificare la collisione di ogni carattere della mesh non è dispendioso, visto che le mesh sono relativemente piccole e hanno un tetto di grandezza massimo, il quale è molto esiguo. Inoltre, era necessario dover controllare ogni char, altrimenti ci sarebbero potute essere imperfezioni ottiche importanti, considerando che il gioco si basa sul render di caratteri molto grandi. Avrei potuto ottimizzare aggiungendo degli algoritmi in grado di valutare le collisioni a priori, come algoritmi di broad phase, per poi passare alla verifica della collisione per-char, ma non era necessario. Inoltre, la CCDPC mi permette di realizzare meccaniche divertenti per un platformer nonostante i suoi limiti. Dal punto di vista tempistico era la scelta migliore.

    🛠️ HOW

    Collisione mappa (righe 174-351) — algoritmo per asse Y positivo (caduta):

    Collisione mappa (Gravità semplificata) 
    void entity::check_map_collision(wchar_t** map, int level_height, int level_width) {
    reset_collision_states();
    int translate_x = speed_x;
    int translate_y = speed_y;

    if (translate_y > 0) {  // Caduta
        int piedi_y = sprite_height - 1;  // Solo i piedi
        bool collided = false;
        for (int step = 1; step <= speed_y; step++) {
            for (int x = 0; x < sprite_width; x++) {
                int coll_y = this->y + piedi_y + step;
                int coll_x = this->x + x;
                wchar_t tile = (coll_x >= level_width || coll_y >= level_height) 
                    ? NO_CHAR : map[coll_y][coll_x];
                
                // Anti-tunneling: se già colliso e ora vuoto → stop immediato
                if (collided && tile == L' ') {
                    translate_y -= speed_y - (step - 1);
                    step = speed_y; break;
                }
                
                if (tile == L'=' || tile == L'I' || tile == NO_CHAR) {
                    set_collision_state(COLLISION_TYPE_GROUND);
                    collided = true;
                    translate_y -= 1;  // Indietreggia di 1
                    break;
                }
            }
        }
    }
    // ... Y negativo (ceiling), X positivo (right), X negativo (left) identici ...
    x += translate_x;
    y += translate_y;
}

    Punti chiave:

    • collided flag previene tunneling: una volta toccato solido, se step successivo trova vuoto → stop immediato (evita "uscire" dal muro dall'altra parte ad alta velocità)

    • Solo punti rilevanti: piedi_y per ground, testa_y=0 per ceiling, limite_destro_x per right, 0 per left — non controlla tutta bbox ogni step

    • Out-of-bounds = muro (NO_CHAR trattato come solido) → entità non esce dal livello

    • Ritorna flag per fisica: is_colliding(COLLISION_TYPE_GROUND) abilita salto, RIGHT_SIDE blocca movimento dx

    Collisione entità-entità (righe 356-371, 728-777) — AABB + double dispatch manuale:

    Collisione entita-entita (AABB) 
    // Base: AABB overlap test — righe 356-366
bool entity::check_entity_collision(entity* e1) {
    return (x < e1->x + e1->bounding_box_width  &&
            x + bounding_box_width  > e1->x &&
            y < e1->y + e1->bounding_box_height &&
            y + bounding_box_height > e1->y);
}

virtual void evaluate_collision(entity* e1) = 0;

void player::evaluate_collision(entity* e) {  // Player vs Enemy
    if (e->entity_type == ENTITY_ENEMY) { hp--; e->destroy = true; }
}
void enemy::evaluate_collision(entity* e) {   // Enemy vs Bullet
    if (e->entity_type == ENTITY_ALLY_BULLET) { e->destroy = true; destroy = true; }
}
void bullet::evaluate_collision(entity* e) { }  // Bullet: logica in map collision + lifetime

    Vantaggi: Zero dynamic_cast, zero RTTI, entity_type = unsigned char → branch prediction friendly, cache-friendly.

    🎮 Il Player | Input, Fisica Arcade, Bullet Management

    🧭 CONTEXT

    Il player era l'entità "tuttofare". Input da tastiera (freccie + Z + Spazio), fisica (gravità, attrito, salto), state machine bitmask, gestione proiettili (max 1 alla volta, spawn da posizione arma), collisione mappa + entità, rendering con flip orizzontale.

    I proiettili hanno richiesto un po' di test, poiché un numero troppo alto di munizioni rendeva tutto troppo semplice, inoltre, lo spawn dei proiettili era pieno di edge-cases da risolvere, ad esempio: "Se provo a sparare mentre sono davanti ad un muro?"

    ❓ WHY?

    Perché fisica "arcade" (attrito lineare, gravità clamped) invece di un approccio physics based?

    Assolutamente non necessario, il sistema scelto mi permette di realizzare un feeling classico del gioco, perfettamente in linea con gli obiettivi di design del gioco. Inoltre, il limite era il terminale stesso, non potevo avere numeri con la virgola, non servivano a niente, non potevano essere considerati durante i movimenti sulla tilemap, basata su numeri interi.

    📽️ Rendering Pipeline | Double Buffering + Virtual Camera + ASCII Sprites

    🧭 CONTEXT

    All'inizio usavo system("cls") + cout per stampare tutto. Chiaramente era tutto sballato, la console sfarfallava e il cursore si muoveva dentro la console.

    Poi il problema della camera, in sostanza dovevo realizzare a tutti gli effetti un "frustum", dato un livello 400×30 e uno schermo 130×30. Chiaramente devo renderizzare solo la regione di mappa interessata alla grandezza dello schermo.

    Oltre a questo problema, dopo aver pensato a renderizzare, dovevo stampare le entità sopra la mappa e comporre il "frame" finale per poterlo renderizzare, senza contaminare la struttura originale della mappa. Per questo ho fatto: tre buffer separati.

    • map = dati livello immutabili (da file). wchar_t**

    • buf = composizione frame corrente (map + entità in coordinate mondo). wchar_t**

    • screen = buffer lineare 1D per WriteConsoleOutputCharacter. wchar_t*

    ❓ WHY?

    Perché double buffering manuale (map → buf → screen)?

    Era necessario dividere la responsabilità, in memoria mi serviva un copia immutabile della mappa per poter effettuare la CD, poi mi serviva una versione per comporre la scena ufficiale, stampando entità e proiettili, senza influenzare la versione immutabile della mappà. Inoltre era necessario avere un buffer in più per renderizzare sulla regione visibile disponibile (la grandezza del terminale).

    Perché WriteConsoleOutputCharacter invece di std::cout?

    Ovviamente molto più ottimizzato, una singola syscall, piuttosto che una quantità altissima per colpa di std::cout, inoltre evito il flicker del cursore ed ho controllo totale sulla posizione dei cratteri.

    🛠️ HOW

    Level buffers (righe 815-842, 864-908):

    Qui componiamo la scena finale, renderizziamo solo la porzione interessata e generiamo l'array finale da passare WriteConsoleOutputCharacter.

    Level buffers (double buffering) 
    class level {
    wchar_t** map;  // Da file, never changes
    wchar_t** buf;  // Frame corrente
    
    void refresh_buffer() {  // Chiamato ogni frame
        for (y) for (x) buf[y][x] = map[y][x];
    }
    
    void draw(wchar_t* screen, camera* cam) {
        for (int y = 0; y < SCREEN_HEIGHT; y++) {
            for (int x = 0; x < SCREEN_WIDTH; x++) {
                int src_x = cam->pan_x + x;
                int src_y = cam->pan_y + y;
                // FRUSTUM CULLING implicito
                if (src_x >= level_width || src_y >= level_height)
                    screen[y * SCREEN_WIDTH + x] = L' ';
                else
                    screen[y * SCREEN_WIDTH + x] = buf[src_y][src_x];
            }
        }
        screen[SCREEN_WIDTH * SCREEN_HEIGHT - 1] = L'\0';
    }
};

    La camera si centra al giocatore, se non supera la prima, tranne quando si trova ai limiti del livello, lì non si muove, non mantenendo il giocatore al centro

    📦 Memory Management | RAII Manuale per Array 2D + Ownership Semantics

    🧭 CONTEXT

    Per il memory management, ho utilizzato strategie classiche, per le entità significava allocare e distruggere nei rispettivi costruttori e distruttori, per la mappa e i buffer, lo stesso.

    Questo significa, nel caso dei buffer, che all'avvio si inizializzassero alla grandezza della hmappa corrispondente, dunque, la grandezza del buffer dipendeva dalla grandezza complessiva della mappa, descritta dai parametri passati durante l'inizializzazione (level_width e level_height). Dopodiché, la mappa veniva letta e immagazzinata in memoria.

    Un procedimento analogo viene applicato per instanziare le sprite delle entità.

    🛠️ HOW

    ~entity() {
    if (sprite_height == 1 && sprite_width == 1) {  // Bullet 1x1
        delete sprite[0];
        delete sprite;
    } else {  // Sprite rettangolare

    Level map/buf (righe 828-862):

    Level map/buf (allocazione) 
    level(int w, int h) : level_width(w), level_height(h) {
    buf = new wchar_t*[level_height];
    map = new wchar_t*[level_height];
    for (int i = 0; i < level_height; i++) {

    ⬇️ Game Loop | Fixed Timestep Polling + Single-Threaded Deterministic

    🧭 CONTEXT

    Il gameloop sfrutta semplici risoluzione per ovviare a problemi legati al timing e alla mancanza di framecap. Ad esempio, l'update degli input è letto ogni frame, ma eseguito a 6fps, per ovviare a problemi come velocità supersoniche.

    L'ordine del frame è costruito nel seguente modo:

    1. Destroy check (bullet morti)

    2. Input → stato + velocità

    3. Physics update

    4. Collision resolution (map & entity, separatamente)

    5. Camera follow

    6. Win check

    7. Render composition

    ❓ WHY?

    Perché questo ordine?

    L'ordine segue una logica molto precisa, garbage collecting, input gathering, update dei movimenti, risoluzione delle collisioni. La sequenza è molto precisa poiché la logica è rigida, eseguire la valutazione delle collisioni PRIMA del potrebbe rompere certe sezioni di gioco, poiché il transform potrebbe essere in una posizione non valida fino al prossimo check delle collisioni.

    💀 Post Mortem

    Limiti di conoscenza

    In quanto è stato il mio primo progetto "Axioverse" presenta palesi problemi dovuti all'inesperienza e ad una mancanza di conoscenze, banalmente, basti pensare al fatto che ho utilizzati puntatori puri senza alcun motivo, quando le librerie standard forniscono gli smart pointers. Questi limiti, mi hanno permesso di comprendere le mie lacune e di proseguire affinando la mia conoscenza e dando preferenza ad una ricerca pre-creazione di una feature, per valutare una mancanza di conoscenze, oltre che, avermi fatto capire di dover continuare a studiare!

    Asset pipeline

    Il loader delle sprite è chiaramente molto fragile, oltre ad utilizzare file di testo, non tiene conto di possibili errori all'interno dei file e caratteri invalidi, non ha bounds che limitino il caricamento di file troppo grandi, non riconosce se il file è vuoto, in sostanza, si fida. Un sistema robusto valuterebbe tutto: dimensioni, caratteri blacklistati/whitelistati, tutto supportato da un sistema di logging chiaro e facile da leggere.

    L'architettura che non c'è

    La mancanza di suddivisione di file, la mancanza di suddivisione fra .h e .cpp, la mancanza di una file structure statica feature-based, classi senza single-responsibility, fiducia negli input, codice monolitico, insomma, si vede che è un primo progetto insieme alla mancanza di un engine. Nei progetti futuri, tutto questo non è più presente, l'architettura, oltre che essere documentata, è definita priori, non in corso d'opera, basti guardare i progressi fatti in Rumble Smash.

    Belli i "magic numbers", no, scherzo

    Il progetto è pieno di magic numbers buttati qui è lì, vi immaginate un game designer che mette mano su questo codice? No, infatti nessuno l'ha fatto. Oltre ai magic numbers, c'è un coupling troppo aggressivo con dinamiche hardware e software, per intenderci, molte variabili riguardano sono pixel-bound o frame-bound, sono difficili da debuggare e per i game designer impossibili da comprendere. La soluzione sarebbe stata creare un'infrastruttura physics-based.

    Commenti, style guide e documentazione

    Leggendo il codice, i commenti non sono del tutto assenti, anzi, spiegano in modo quasi esaustivo certe parti del gioco, ma non è stata un'abitudine mantenuta in tutti i punti. Per questo alcuni punti dell'architettura e' poco chiaro, non è possibile comprendere chiaramente il "perché" dietro certe scelte, oppure, semplicemente il loro funzionamento.

    Il vero problema, però, risiede nella mancanza di una style guide che ha reso difficile la lettura e il debugging, a posteriori, avere una style guide mi aiuta a ridurre il carico cognitivo a zero sulla forma, così tutto il cervello va sul contenuto, piuttosto che su ogni inconsistenza, inoltre aumenta l'ordine mentale e la schematizzazione, rendendo il codice più facile da ricordare.

    Oltre che una style guide, mancava una documentazione, chiaramente, anche qui i downsides sono ovvi, mancava una mappa per poter comprendere il codice da esterno, ormai per me è inaccettabile non averla, motivo per cui sarà onnipresente nei futuri progetti.
