🗿 State Machine at Bitmask | Bitwise Flags & Manual State Management

🧭 CONTEXT

So, the player. I had to know if he was standing still, running, jumping, fell, shot. Obviously, the right answer was to use a state machine, perhaps exploiting an architecture divided into classes which then converged, by composition, into a script that managed them. How made for RumbleSmash - Portfolio - IT|Rumble Smash.

But, I'm cool 😎.

So, I opted to manage states through i bit (mi I'm having fun, right?) and bitmasks. Theoretically through one approach classic for state machines, if I'm jumping and shooting and let's assume that when I'm in this state I take double damage, I can create a new pseudostate to manage special interactions and behaviors, thus solving this problem.

Instead, with bitmasks it is slightly different, because to check if I I'm in two states at the same time, I just need to apply two masks to myself same time.

Suppose that

States 
// 8 bit, ogni bit rappresenta uno stato.
unsigned char current_active_states = 0;

const int STATE_STILL     = 0b1;
const int STATE_RUNNING   = 0b10;
const int STATE_JUMPING   = 0b100;
const int STATE_FALLING   = 0b1000;
const int STATE_SHOOTING  = 0b10000;

To manage the behaviors deriving from the activation of 2 states or more I do:

Check the status 
if ((current_active_states & STATE_JUMPING) && (current_active_states & STATE_SHOOTING))
{
	damageMultiplier = 2f;
}

❓ WHY?

Why bits and bitmasks instead of enum/state patterns classic?

The real reason was to learn how to manage the bits and manipulate them, so it was more a case study than a real architectural choice, but let's see however what advantages exist in this architecture.

  • Coexistence of states: collision_mask can have GROUND | RIGHT_SIDE together, with other methods I should create pseudostates.

  • Performance: state_mask & STATE_JUMPING Binary operations are very simple, in practice perfect if I want to program ROMs for my beloved Game Boy Advance (it's success), where optimization is the basis.

  • Memory: 1 unsigned char means 8 states in 1 byte.

  • Extensibility: add STATE_DASHING = 0b100000 not tap existing code,

Also, the simplicity of the game allowed me to opt for this solution, clearly for more complex systems, I should have adopted other choices.

⚽ Collision System | Per-Char collision detection

🧭 CONTEXT

I had to create collisions within the game, therefore, for a game run in console, the only option was a two-dimensional array of characters. I needed it, as well as having different "blocks", it was necessary that everyone had a different behavior, some "blocks" had to block me the player, others not, if I then wanted to create new behaviors for other blocks, I had to make the code extensible for this purpose.

So, I basically created a "tilemap" made of unsigned char, where:

  • '=': platforms

  • 'I' = walls

  • ' ' = empty.

After solving the map problem, I needed to create a collision system, the idea was to develop a similar AABB with continuous collision detection, the CCD was necessary, otherwise any movement greater than one "tile" would break the collisions. The result is an algorithm that controls the character mesh and that divides the movement into "steps", each of which is verified, not as soon as a collision occurs, the entity is translated by a value equal to the distance between the initial position of the entity and the first one collision occurred, for a project based only on simple shapes, it's perfect, maybe not the best of optimization.

Each step checked, the character mesh is entirely checked the overlap with the map tiles, since the meshes are done from ASCII characters, each character in World Space to check if collisions have occurred. For short, this algorithm of CCD per-char is called CCDPC.

❓ WHY?

Why did you choose the CCDPC algorithm?

Checking the collision of each character of the mesh is not expensive, since meshes are relatively small and have a size ceiling maximum, which is very small. Furthermore, it was necessary to have to check each char, otherwise there could have been optical imperfections important, considering that the game relies on character rendering a lot large. I could have optimized by adding algorithms capable of evaluate collisions a priori, as broad phase algorithms, and then switch to per-char collision checking, but it wasn't necessary. Additionally, the CCDPC allows me to create fun mechanics for a platformer despite its limitations. From a timing point of view it was the best choice.

Collision map (lines 174-351) — algorithm for positive Y axis (fall):

Map Collision (Gravity simplified) 
void entity::check_map_collision(wchar_t** map, int level_height, int level_width) {
    reset_collision_states();
    int translate_x = speed_x;
    int translate_y = speed_y;

    if (translate_y > 0) {  // Caduta
        int piedi_y = sprite_height - 1;  // Solo i piedi
        bool collided = false;
        for (int step = 1; step <= speed_y; step++) {
            for (int x = 0; x < sprite_width; x++) {
                int coll_y = this->y + piedi_y + step;
                int coll_x = this->x + x;
                wchar_t tile = (coll_x >= level_width || coll_y >= level_height) 
                    ? NO_CHAR : map[coll_y][coll_x];
                
                // Anti-tunneling: se già colliso e ora vuoto → stop immediato
                if (collided && tile == L' ') {
                    translate_y -= speed_y - (step - 1);
                    step = speed_y; break;
                }
                
                if (tile == L'=' || tile == L'I' || tile == NO_CHAR) {
                    set_collision_state(COLLISION_TYPE_GROUND);
                    collided = true;
                    translate_y -= 1;  // Indietreggia di 1
                    break;
                }
            }
        }
    }
    // ... Y negativo (ceiling), X positivo (right), X negativo (left) identici ...
    x += translate_x;
    y += translate_y;
}

Key points:

  • collided flag prevents tunneling: once it hits solid, if next step finds empty → stop immediate (avoids "coming out" of the wall on the other side at high speed)

  • Relevant points only: feet_y for ground, testa_y=0 for ceiling, right_limit_x for right, 0 for left — does not control all bbox every step

  • Out-of-bounds = wall (NO_CHAR treated as solid) → entity does not exit the level

  • Return flag for physics: is_colliding(COLLISION_TYPE_GROUND) enable skip, RIGHT_SIDE block right movement

📽️ Rendering Pipeline | Double Buffering + Virtual Camera + ASCII Sprites

🧭 CONTEXT

At first I used system("cls") + cout to print everything. Clearly everything was wrong, the console was flickering and the cursor was moved inside the console.

Then the problem of the camera, essentially I had to realize all the effects a "frustum", given a 400×30 level and a 130×30 screen. Clearly I have to render only the map region concerned screen size.

In addition to this problem, after thinking about rendering, I had to print the entities above the map and compose the final "frame" to be able to render, without contaminating the original structure of the map. For I did this: three separate buffers.

  • map = data level immutable (from file). wchar_t**

  • buf = frame composition current (map + entity in world coordinates). wchar_t**

  • screen = linear buffer 1D for WriteConsoleOutputCharacter. wchar_t*

❓ WHY?

Why manual double buffering (map → buf → screen)?

It was necessary to divide the responsibility, in memory I needed a copy immutable of the map to be able to make the DC, then I needed one version to compose the official scene, printing entities and projectiles, without affecting the immutable version of the map. It was also necessary have an extra buffer to render on the available visible region (the size of the terminal).

Why WriteConsoleOutputCharacter instead of std::cout?

Obviously much more optimized, a single syscall, rather than a very high quantity due to std::cout, furthermore I avoid the cursor flicker and I have total control over the position of the characters.

🛠️ HOW

Level buffers (lines 815-842, 864-908):

Level buffers (double buffering) 
class level {
    wchar_t** map;  // Da file, never changes
    wchar_t** buf;  // Frame corrente
    
    void refresh_buffer() {  // Chiamato ogni frame
        for (y) for (x) buf[y][x] = map[y][x];
    }
    
    void draw(wchar_t* screen, camera* cam) {
        for (int y = 0; y < SCREEN_HEIGHT; y++) {
            for (int x = 0; x < SCREEN_WIDTH; x++) {
                int src_x = cam->pan_x + x;
                int src_y = cam->pan_y + y;
                // FRUSTUM CULLING implicito
                if (src_x >= level_width || src_y >= level_height)
                    screen[y * SCREEN_WIDTH + x] = L' ';
                else
                    screen[y * SCREEN_WIDTH + x] = buf[src_y][src_x];
            }
        }
        screen[SCREEN_WIDTH * SCREEN_HEIGHT - 1] = L'\0';
    }
};

The camera centers on the player if it does not exceed the first, except when located at the limits of the level, there it does not move, not keeping the player at the center

📦 Memory Management | RAII Manual for 2D Arrays + Ownership Semantics

🧭 CONTEXT

For memory management, I used classic strategies, for entities meant allocate and destroy in the respective constructors and destroyers, for the map and the buffers, the same.

This means, in the case of the buffers, that they initialize themselves at startup the size of the corresponding hmap, therefore, is the size of the buffer it depended on the overall size of the map, described by the parameters passed during initialization (level_width and level_height). After that, the map was read and stored in memory.

A similar procedure is applied to instantiate the sprites of entity.

⬇️ Game Loop | Fixed Timestep Polling + Single-Threaded Deterministic

🧭 CONTEXT

The gameloop uses simple resolutions to overcome problems related to timing and lack of framecap. For example, the input update is read every frame, but run at 6fps, to overcome issues such as speed supersonic.

The frame order is constructed as follows:

1. Destroy check (dead bullets)

2. Input → status + speed

3. Physics update

4. Collision resolution (map & entity, separately)

5. Camera follow

6. Win check

7. Render composition

❓ WHY?

Why this order?

The order follows a very precise logic, garbage collecting, input gathering, movement update, collision resolution. The sequence is very precise since the logic is rigid, perform the evaluation of collisions BEFORE of may break certain sections of the game, as the transform may be in an invalid position until the next time collision check.

💀 Post Mortem

Limitations of knowledge

Since it was my first project "Axioverse" presents obvious problems due to inexperience and a lack of knowledge, trivially, just think about the fact that I used pure pointers without them no reason, when standard libraries provide smart pointers. These limits allowed me to understand my shortcomings and to continue by refining my knowledge and giving preference to research pre-creation of a feature, to evaluate a lack of knowledge, further which, made me understand that I had to continue studying!

Asset pipeline

The sprite loader is clearly very fragile, in addition to using text file, it does not take into account possible errors within the files and invalid characters, has no bounds that limit file loading too large, it does not recognize if the file is empty, essentially, it trusts. A system robust would evaluate everything: size, fonts blacklisted/whitelisted, all supported by a clear logging system and easy to read.

The architecture that isn't there

The lack of file splitting, the lack of splitting between .h and .cpp, the lack of a feature-based static file structure, classes without single-responsibility, trust in inputs, monolithic code, in short, yes sees that it is a first project together with the lack of an engine. Nei future projects, all this is no longer present, architecture, as well as be documented, it is defined priori, not in progress, just look the progress made in Rumble Smash.

The "magic numbers" are nice, no, I'm joking

The project is full of magic numbers thrown here and there, you imagine a game designer who puts his hand on this code? No, in fact no one has done. In addition to the magic numbers, there is too aggressive coupling with hardware and software dynamics, so to speak, many variables concern they are pixel-bound or frame-bound, they are difficult to debug and for games designers impossible to understand. The solution would have been to create a physics-based infrastructure.

Comments, style guides and documentation

Reading the code, the comments are not completely absent, on the contrary, they explain almost exhaustively certain parts of the game, but it wasn't a habit maintained at all points. For this reason some points of architecture are unclear, it is not possible to clearly understand the "why" behind certain choices, or simply their functioning.

The real problem, however, lies in the lack of a style guide which has made reading and debugging difficult, in hindsight, having a style guide helps me to reduce the cognitive load to zero on the form, so the whole brain goes on the content, rather than on any inconsistency, it also increases mental order and schematization, rendering the code easier to remember.

In addition to a style guide, documentation was clearly missing too here the downsides are obvious, there was no map to understand the code as an outsider, it is now unacceptable for me not to have it, which is why it will be omnipresent in future projects.
